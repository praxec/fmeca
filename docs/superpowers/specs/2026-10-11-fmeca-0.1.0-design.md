# fmeca 0.1.0 — design spec

**Status:** approved design, transcribed. Source of authority: epic praxec/fmeca#12 (design agreed in a cpm-planner session, 2026-10-11) and tickets #13–#26, milestone `0.1.0`. This spec does not reopen any decision in the epic. Where the epic leaves a detail open, this spec records a **proposed default** (marked ⓟ), to be confirmed in the owning ticket's PR.

**Amended:** §6 (maintainer decisions, 2026-10-11) adds the `.fmeca/` project store, resolution tracking and level-based skills. Where §6 conflicts with §4.5 (skill list) or §5 (schedule), §6 wins.

**Goal:** release fmeca 0.1.0, with the repository ready for open source, agent skills plus a guide for installing them, and advisory Jev vetting through OpenRouter, without breaking anything Junior relies on.

## 2. Invariants (every ticket, every review)

1. **Junior contract is frozen.** Repo `praxec/fmeca`; binary `fmeca-mcp` (`fmeca-mcp.exe` on Windows); archives `fmeca-mcp-<triple>.tar.gz` for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin` and `fmeca-mcp-<triple>.zip` for `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`; release asset `checksums.sha256` (`<hex>  <name>` lines, one for every archive); MCP tools `session.open`, `append`, `state.get`, `risk.next`, `readiness.assess`, `report.export`, `scoring.catalog`, `analyze` with compatible inputs and outputs. New tools and flags are additions only.
2. **Kernel purity.** The `fmeca` crate gains no dependency and makes no network calls. CI asserts that `cargo tree -p fmeca` contains neither `rig` nor `reqwest`.
3. **Jev is never an input.** No model supplies a score. `vet` never appends to the event log and never changes criticality, residual, standing, readiness or export output.
4. **No-arg behaviour unchanged.** `fmeca-mcp` with no arguments runs the stdio MCP server exactly as it does today.
5. **Secrets.** `OPENROUTER_API_KEY` is read only from the environment. It is never logged, echoed in errors or tool output, or written into a config file or doc snippet as a literal.
6. **Gates.** `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` (locally; CI keeps clippy advisory per `21a647e` unless #13 decides otherwise), `cargo test` on Linux, macOS and Windows, plus every job a ticket adds.
7. **Tests.** Declarative names, one behavioural assertion each, no network in default tests. Live tests are `#[ignore]` and run only when `OPENROUTER_API_KEY` is set.

### 4.3 Jev client (#22 spike, #23 module)

The PR records request/response shapes, latency, `usage.cost`, the dependency tree and the binary-size delta, and which client path #23 uses. If rig's wire format is rejected, the fallback is a thin client that uses the same typed `Query` structs over direct HTTP, plus an upstream rig issue. The findings are also posted to praxec/cpm-planner (its P6 spike).
- **Module:** `crates/fmeca-mcp/src/jev/` behind cargo feature **`jev`**, ported from cpm-planner `src/llm/{mod,jev}.rs` (copy and adapt, not a shared crate). It drops the key file, the generative chat client and the endpoint override env var; the endpoint stays a constructor argument so the mock server can inject it. `jev` is in the `default` features so that release, Docker and npm binaries include it, while `--no-default-features` builds a server without it. It provides:
  - a `JudgmentModel` trait (Noul, Score, Choice),
  - the OpenRouter implementation chosen by the spike,
  - a `FakeJudge` for tests,
  - `JevConfig::from_env()` reading `OPENROUTER_API_KEY`, `FMECA_JEV_MODEL` (default `typesafe/jev-1.13`) and `FMECA_JEV_TIMEOUT_SECS` (default 30), with no key file and a redacted `Debug`.
  - `Unavailable { reason }` errors, where `reason` is one of `no_key`, `timeout`, `http_4xx`, `http_5xx`, `network` or `bad_response`.

  Tests run against the fake and a local mock HTTP server (`httpmock` or `mockito`, dev-dependency), plus one `#[ignore]` live test.

### 4.4 `vet` MCP tool (#24)
- **Input:** `{ session_id?: string, analysis?: <analyze input>, checks?: ["observations"|"mitigations"|"coverage"|"readiness"], max_questions?: integer }`. Exactly one of `session_id` and `analysis` must be present, enforced in the handler; the schema has **no top-level `oneOf`**. `checks` defaults to all four. `max_questions` defaults to 40, and the cap applies before any call.
- **Question construction is deterministic.** Failure modes are processed in id order, checks in the fixed order above, and items within a check in id order. `question_hash` = sha256 of the canonical JSON of `{check, target, question, state}`. Questions beyond the cap are listed in `skipped` and are never sent.
- **Checks:**
  - *observations:* one Noul per claimed observation, given the failure mode's cause, effect and description. It also asks about a fixed, small set of **unclaimed** catalog observations on each axis, so under-scoring is caught as well as over-scoring. ⓟ The set is the catalog criteria one level above the highest claimed level on that axis (at most one per axis), chosen deterministically from the session's matrix strategy.
  - *mitigations:* per mitigation, one Score (does it address the cause?) and one Choice over `prevention | detection | fail_fast`, compared with the declared `kind`.
  - *coverage:* one Score per entry of a fixed failure-class catalog, asking whether the class plausibly applies but is not covered. ⓟ The catalog is `data_integrity`, `concurrency`, `external_dependency`, `security`, `resource_exhaustion`, `configuration`, `operator_error`, finalised in the PR. Results are candidates only; Jev never invents failure modes, and the agent decides whether to `append`.
  - *readiness:* one Score that the analysis is sound enough to sign off, returned beside the deterministic `readiness.assess` result without changing it.
- **Output:** `{ status: "ok", findings: [{check, target, question_hash, probability, threshold, verdict}], readiness_gate: <readiness.assess result>, model, usage: {cost, …as reported}, skipped: [question_hash…] }`. ⓟ Default thresholds, all published as constants and echoed per finding:
  - a claimed observation is flagged when p(applies) < 0.3;
  - an unclaimed observation is flagged when p(applies) > 0.7;
  - a mitigation is flagged when Score(addresses cause) < 0.5, or when the Choice argmax ≠ the declared `kind` with p ≥ 0.6;
  - a coverage gap is flagged when Score ≥ 0.6;
  - the readiness verdict is `concern` when Score < 0.5.
- **Failure:** no key, outage, 4xx or timeout returns `{ status: "vet_unavailable", reason }` with `isError: false`, never an error that blocks analysis.
- **Invariant tests:** fold the same log before and after `vet` and check that `state.get`, `risk.next`, `readiness.assess` and `report.export` are byte-identical and the log length is unchanged; the unavailable paths; deterministic order and hashes; the cap with many failure modes; and the schema has no `oneOf`.

### 4.5 Agent skills (#18) and `skills install` (#19)
- *(Skill list superseded by §6.4.)* `skills/<name>/SKILL.md` (Agent Skills format) for `fmeca` (the method reference), the five level skills, `fmeca-resolve`, `fmeca-vet` and `fmeca-signoff`, modelled on cpm-planner's `skills/cpm-*` and `deliverable-cpm`. ## 6. Amendment (2026-10-11, maintainer): project store, resolution tracking, levels

These decisions came from the maintainer in the planning session, after the epic. They are folded into **0.1.0**. They add three tickets, #27–#29 (created 2026-10-11 under milestone 0.1.0 and listed on epic #12), and they reshape #18, #21 and #24. The Junior contract is unchanged: every change is an addition (optional fields, new event types, a new `append` variant, new tools, new subcommands), and Junior always sets `FMECA_STATE_DIR` itself. **Forward-compatibility note:** a log that contains the new events cannot be replayed by fmeca ≤ 0.0.2. CHANGELOG and SECURITY state this.

### 6.1 Analyses live in the repo: `.fmeca/` (#28, project store)
- **State-dir resolution** (first match wins):
  1. `FMECA_STATE_DIR`;
  2. the nearest `.fmeca/` directory found walking up from the process working directory;
  3. today's user default (`$XDG_DATA_HOME/fmeca-mcp`, `~/.local/share/fmeca-mcp`);
  4. `./fmeca-state`.

  The server logs at startup which rule applied, on stderr.
- **Layout:** flat and unchanged. Each analysis is `.fmeca/<session_id>.jsonl`, one append-only event per line, so many analyses sit side by side and diff cleanly in git. Session ids keep today's rules (no `/`, no leading `.`). The convention is `<aspect>-<level>`, e.g. `checkout-technical-plan`.
- **`fmeca-mcp init [--dir <project-root>]`** creates `.fmeca/README.md` (what the folder is, how to read and resume analyses) and `.fmeca/.gitattributes` containing `*.jsonl text eol=lf merge=union`. Union merge keeps both branches' appended events. Running it twice is safe: it reports `created` or `unchanged` per file and never overwrites a file that already exists.
- **`fmeca-mcp check [--dir <state-dir>]`** replays every `*.jsonl` and prints `ok <session_id>` or `error <session_id>: <reason>`. It exits 1 if any log fails, for example because a union merge produced a duplicate failure-mode id. It is meant for CI and pre-commit use.

### 6.2 Analysis metadata, levels and links (#27 kernel, #29 server)
- **`AnalysisLevel`** (snake_case): `concept`, `conops`, `technical_plan`, `project_plan`, `implementation`, `verification`.
  - `concept`: what the thing is and why: value, users, harms.
  - `conops`: the business-level concept of operations: actors, workflows, operating scenarios.
  - `technical_plan`: how the technology is used: architecture, interfaces, dependencies.
  - `project_plan`: the deliverables and their sequencing, linked to cpm-planner deliverables.
  - `implementation`: code, modules, diffs and PRs.
  - `verification`: tests, rollout and operations evidence.
- **`SessionMeta`** `{ title?, level?, aspect?, scope_paths: [string], parent?: session_id }` is recorded in `SessionOpened` (`#[serde(default)]`, so old logs replay with empty metadata). `session.open` accepts these fields as optional arguments.
- **Links:**
  - a session may name a `parent` session (e.g. a technical plan under its conops);
  - a failure mode may carry `parent: { session_id, failure_mode_id }` (the risk it refines) and `refs: [string]` for external anchors: `cpm:<plan_id>/<deliverable_id>`, `path:<file>`, `issue:<url>`, `pr:<url>`, `commit:<sha>`.
  - Parent links are validated when appended (the parent session or failure mode must exist) but not on replay, so logs stay portable.
- **New tool `session.list { level?, aspect?, parent? }`.** It returns one row per analysis: `session_id`, the metadata, counts by standing, `ready`, `ready_verified`, and resolution counts. It also returns `state_dir`. The kernel gains `StateStore::list_sessions()`, which `FilesystemStore` implements.

### 6.3 Resolution tracking (#27 kernel, #29 server)
- **New `append` variant `set_mitigation_status`** `{ session_id, mitigation_id, status: planned|implemented|verified|abandoned, evidence?: [{kind: commit|pull_request|test|file|url|note, reference}], note? }`. It becomes the event `MitigationStatusChanged`. The server stamps `at` with the UTC time in RFC 3339. The kernel stores it as data; the kernel itself never reads a clock.
  - Every mitigation starts as `planned`.
  - `verified` needs at least one evidence item whose kind is not `note`.
  - Any transition is allowed, and every change is kept in the mitigation's `history`.
- **Views:** each mitigation in `state.get` and `report.export` gains `status`, `evidence` (accumulated) and `history`. Each failure mode gains `verified_residual_criticality`, the best residual among `verified` mitigations, or the raw criticality if there are none.
- **Abandoned mitigations** no longer count toward residual risk. This is the only change to existing computation, and it applies only to logs that use the new event.
- **Readiness keeps its existing fields and meaning** and adds two:
  - `resolution { planned, implemented, verified, abandoned }`;
  - `verified { ready, blockers }`, the same gate computed from verified mitigations only.

  Sign-off at the `verification` level uses `verified.ready`.

### 6.4 Skills by level (#18 reshaped)
The skills are as follows. One `fmeca-concept` skill covers both business-level levels (`concept` and `conops`), which gives five level skills. This follows the maintainer's 2026-10-11 decision, and NASA does not separate the two either (§6.6).
- `fmeca`: the method reference. It adds the levels table, the `.fmeca/` layout, linking conventions and the resolution lifecycle.
- Level skills: `fmeca-concept` (it decides from the input whether to open a `concept` analysis, a `conops` analysis with the concept as parent, or both in sequence), `fmeca-technical-plan`, `fmeca-project-plan`, `fmeca-implementation` and `fmeca-verification`. Each covers:
  - what to read (idea or brief; operating scenarios; design doc; plan or cpm graph; diff or module; test reports and rollout);
  - the session id and parent to use;
  - typical domains;
  - what counts as a mitigation at that level and what evidence verifies it;
  - the analyse → `risk.next` → mitigate loop.

  `fmeca-project-plan` reads the cpm-planner plan (`plan.status`) when one exists and puts `cpm:` refs on failure modes.
- `fmeca-resolve`: moves mitigations through `set_mitigation_status` with evidence, e.g. after a PR merges or a test lands.
- `fmeca-vet` and `fmeca-signoff`: as before. `fmeca-signoff` presents `verified.ready` beside `ready`.

The activity skills `fmeca-analyze` and `fmeca-mitigate` are dropped; their loop moves into the reference and the level skills. `skills install` (#19) embeds whatever `skills/` contains, so #19 changes nothing except the expected file lists in tests.

### 6.6 NASA-informed additions (maintainer, 2026-10-11)
These come from NASA practice: GSFC-HDBK-8004 (Aug 2024), NASA-STD-8729.1A and MIL-STD-1629A. The research notes are summarised here, with sources in those documents. Everything is optional or has a serde default, so old logs replay unchanged. They are owned by #27 (kernel) and #29 (server).

1. **Effects at three levels.** `FailureMode` gains optional `local_effect` and `next_effect`. The existing `effect` is the **end** effect. This follows MIL-STD-1629A's local / next higher / end effect and GSFC's local / next / ultimate. When a failure mode has a `parent`, its `next_effect` should describe how it shows up as the parent's `cause`. This is how a lower-level analysis feeds a higher one (GSFC §4.4).
2. **Failure-mode disposition** (new event `FailureModeDispositioned`, new `append` variant `set_failure_mode_disposition`): `{ failure_mode_id, disposition: open|accepted|excluded, rationale, approver?, evidence?, at }`.
   - **`accepted`** means the residual risk is retained on purpose, as with NASA's CIL retention and waiver. It needs a non-empty `rationale` and an `approver`. An accepted failure mode stops blocking both readiness gates and is listed in `readiness.accepted_risks`.
   - **`excluded`** means not credible, as with GSFC's likelihood 0 and Exclusion Table. It needs a `rationale` and at least one evidence item that is not a note. An excluded failure mode leaves `risk.next`, the standing counts and the gates; it is listed in `readiness.excluded` and kept in history, never deleted.
   - **`open`** reverts either one.
   - Every change goes into the failure mode's `disposition_history`.
3. **Evidence basis.** `ResolutionEvidence` gains an optional `basis`: `design|test|inspection|failure_history|operational_use`. These are NASA's retention-rationale categories. `kind` says where the evidence is; `basis` says why it counts.
4. **Single-point failures.** `FailureMode` gains `single_point: bool` (default false). Readiness and export gain `critical_items`: the ids of failure modes that are `single_point`, whose raw criticality is High, and that are not excluded. This follows GSFC's SPF table and Critical Items.
5. **The existing model already matches NASA in three ways:**
   - one analysis per level, linked between analyses (GSFC keeps the level fixed within an analysis and links subordinate analyses to superior ones);
   - prevention / detection / fail_fast ≈ GSFC's Prevention / Detection / Mitigation;
   - the append-only re-scoring (`rescore`) records a cited change in likelihood, as GSFC's re-characterisation does.

**Deferred beyond 0.1.0:**
- the GSFC detection/prevention rating (1–5) and RPN;
- readiness expectations per milestone (PDR, CDR, ORR);
- hazard and requirement cross-reference links (use `url` or `note` evidence for now);
- a full CIL report with control plans.

The planned → implemented → verified mitigation lifecycle is our own design; no NASA primary source defines that state machine.
