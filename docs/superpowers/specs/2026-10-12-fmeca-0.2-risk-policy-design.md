# fmeca 0.2 — declarative risk policies and action suggestions (design)

**Status:** design approved in conversation with the maintainer (2026-10-12), section by section; this document records it for review before planning.

**Goal:** given a finished FMECA analysis, let an agent or a person ask *"under this policy, what should we do?"* and get back a deterministic, explainable set of suggested actions, tagged and grouped, with a policy-relative sign-off verdict. fmeca suggests; it never acts.

**Context:** fmeca is used in software development (Junior, Claude Code and other agents; `.fmeca/` analyses in a repo). 0.1.0 computes criticality on a fixed matrix, has a readiness gate, a verified gate, mitigation resolution and failure-mode dispositions. It does not say *what to do* beyond "reduce High/Medium residuals to Low", and that rule cannot be tailored to how important or what type the project is.

---

## 1. Decisions (maintainer, 2026-10-12)

1. **Suggestions only.** fmeca organises and returns suggested actions; agents or humans decide. Nothing is enforced and nothing is written as a consequence of a query.
2. **Declarative, query-time.** Policies are data: built-in presets plus TOML files in `.fmeca/policies/`. A policy is applied when the analysis is *queried*; it is never recorded in the event log, so one analysis can be read under several policies (e.g. `prototype` vs `safety-critical`).
3. **Confidence is derived from evidence**, deterministically, from data already in the analysis. No new caller input, and no model ever supplies a rating (0.1.0's core rule stands).
4. **Shape:** a new pure crate `fmeca-policy`, exposed as MCP tools `actions.suggest` and `policy.list` and as CLI `fmeca-mcp suggest` / `fmeca-mcp policy validate`. The kernel (`fmeca`) is unchanged.
5. **Software-flavoured.** Bands, actions and presets speak software (design review, tests, flags, staged rollout, monitoring, runbooks, ADRs), following NASA and other mature practice without claiming compliance with any standard.

## 2. Grounding in mature practice

Findings from primary sources (NPR 8000.4C, NPR 8705.4A, NPR 7150.2D read in full; MIL-STD-882E in full) and secondary sources where standards are paywalled (AIAG-VDA 2019, ISO 26262, DO-178C, ISO 14971, IEC 61508), and how each shapes this design:

| Practice | Source | Design consequence |
|---|---|---|
| Matrices and their interpretation are defined per project in its Risk Management Plan, not fixed by the standard. | NPR 8000.4C §3.2.2(10) Note 1 | Policies are project data (`.fmeca/policies/`), versioned by content hash. |
| Fixed disposition vocabulary, exactly one per risk: **accept, mitigate, watch, research, close, elevate**; mitigate/watch/research need an owner; accept needs rationale, assumptions and a review interval for those assumptions; watch needs triggers. | NPR 8000.4C §3.4.2(i–j), §3.2.2(12) | Bands declare which dispositions are acceptable; the evaluator *suggests* one; accepted risks get a review interval and a "review due" check. |
| Tailoring by class changes **required process rigour**, not matrix thresholds: payload classes A–D (risk tolerance), software classes A–E with a requirements mapping matrix of invoked vs optional requirements. | NPR 8705.4A §3.1–3.2, App. D; NPR 7150.2D §2.1.6, §2.2.1, App. C | Presets keep a standard matrix and vary which actions are **required** vs **suggested**, minimum confidence and acceptance roles. |
| A standard matrix must be used unless a tailored one is formally approved and *derived from* the standard tables. | MIL-STD-882E §4.3.3(d) | Custom matrices declare `derived_from` a built-in matrix; `policy validate` checks it. |
| Risk Assessment Codes (High / Serious / Medium / Low), with acceptance authority rising with risk and user-representative concurrence for Serious/High. | MIL-STD-882E Table III, §4.3.7 | The `safety-critical` preset uses these bands; bands carry an `acceptance` role and optional `concurrence` roles (suggested, not enforced). |
| Design order of precedence: eliminate by design → reduce by design → engineered features → warning devices → procedures/training; procedural-only mitigation to be avoided for catastrophic/critical hazards. | MIL-STD-882E §4.3.4 | Actions carry a `precedence` (eliminate → prevent → detect → contain → procedure) and are returned in that order; strict presets require higher-precedence actions first. |
| Missing or incomplete verification evidence: the risk contribution is documented at the **worst** level until the work is done or formally accepted. | MIL-STD-882E Table VI | Confidence below a band's minimum makes the failure mode fall back to its **inherent** band ("confidence fallback"). |
| Verification by analysis, test, demonstration or inspection. | MIL-STD-882E §4.3.6; NASA TADI | The confidence ladder ranks evidence; the ordering itself is fmeca's convention (no standard ranks the methods). |
| Action Priority H/M/L replaces RPN; for **H** the team must act *or document why current controls are acceptable*; not acting does not lower the priority. | AIAG-VDA FMEA Handbook 2019 (+ errata) [secondary] | Bands may set `no_action_needs_rationale`; an accepted risk keeps its band. |
| Acceptability criteria (acceptable / ALARP / unacceptable) are set by the organisation in its plan. | ISO 14971:2019 cl. 4.2 [secondary] | Same as 8000.4C: criteria live in the policy, not the code. |
| Re-evaluate when circumstances change, when new failure data shows risk higher/lower than recognised, and at a defined review interval. | NPR 8000.4C §1.2.2.4, §3.2.2(12); MIL-STD-882E §4.3.7 | 0.2 implements the review-interval trigger (`as_of` vs acceptance time); change- and data-driven triggers are noted for later (§9). |

No standard publishes a confidence × risk matrix; the `confidence-view` preset (§6) is fmeca's own, matching the maintainer's example chart.

## 3. The policy document

A policy is TOML, built in or at `.fmeca/policies/<name>.toml`. Its identity is `name` plus `hash` (sha256 of the canonical TOML after parsing), and every query result reports both.

```toml
name = "standard"
description = "Default for production software"
class = "standard"            # free label; presets use prototype|standard|business-critical|safety-critical
schema = 1

[[bands]]
id = "none"
label = "No action"
rank = 0                      # higher = worse; ranks are unique
dispositions = ["close", "accept"]
no_action_needs_rationale = false

[[bands]]
id = "compensate"
label = "Compensating action required"
rank = 1
dispositions = ["mitigate", "watch", "accept"]
no_action_needs_rationale = true
min_confidence = "C1"         # residual counts only at or above this confidence
acceptance = "tech_lead"      # suggested role to accept a risk left in this band
review_interval = "180d"

[[bands]]
id = "review"
label = "Compensating actions with deliverable review and re-evaluation"
rank = 2
dispositions = ["mitigate", "research", "elevate", "accept"]
no_action_needs_rationale = true
min_confidence = "C2"
acceptance = "eng_manager"
concurrence = ["tech_lead"]
review_interval = "90d"

[matrices.nasa8004_5x5]
derived_from = "nasa8004_5x5"
# rows: severity ordinal 1..5 (top = 1); columns: probability ordinal 1..5
cells = [
  ["none",       "none",       "none",       "compensate", "compensate"],
  ["none",       "none",       "compensate", "compensate", "review"],
  ["none",       "compensate", "compensate", "review",     "review"],
  ["compensate", "compensate", "review",     "review",     "review"],
  ["compensate", "review",     "review",     "review",     "review"],
]

[matrices.qualitative3x3]
derived_from = "qualitative3x3"
cells = [
  ["none",       "none",       "compensate"],
  ["none",       "compensate", "review"],
  ["compensate", "review",     "review"],
]

[signoff]
max_residual_band = "compensate"   # effective bands above this fail sign-off unless accepted
accepted_counts_as_pass = true     # an accepted risk does not fail sign-off…
accepted_requires_review_current = true  # …unless its review is overdue

[[actions]]
id = "design-review"
text = "Hold a design review of this failure mode with a second engineer"
tags = ["review", "design"]
precedence = "eliminate"
applies_when = { band_at_least = "review", level_in = ["technical_plan", "implementation"] }
required_when = { class_in = ["business-critical", "safety-critical"] }

[[actions]]
id = "fault-injection-test"
text = "Add a fault-injection or property test that exercises this failure mode"
tags = ["test"]
precedence = "detect"
applies_when = { band_at_least = "compensate", confidence_below = "C3" }
```

**Rules the validator enforces** (`INVALID_POLICY: <field>: <reason>`):
- band ids and ranks are unique; every band referenced by a matrix, `signoff` or an action exists;
- each matrix has exactly N×N cells for its strategy (3×3 or 5×5) and names a built-in `derived_from`;
- the matrix is **monotone**: a cell's band rank never decreases when severity or probability increases (keeps "derived from" honest without forbidding re-colouring);
- confidence values are `C0`…`C4`; durations are `<n>d`; dispositions come from the NASA set;
- `applies_when` / `required_when` use only the keys below;
- unknown keys are rejected (`deny_unknown_fields` everywhere).

**`applies_when` / `required_when` keys** (all optional, all must hold): `band_at_least`, `band_in`, `level_in` (analysis level), `domain_in`, `response_class_in`, `single_point`, `confidence_below`, `confidence_at_least`, `disposition_in` (`open|accepted|excluded`), `fallback` (bool), `class_in` (the policy's class; used for tailoring), `mitigation_kinds_missing` (e.g. `["prevention"]`).
- `rank_at_least` — the effective band's rank is at least N (band-agnostic, for the shared catalog); an unscored failure mode never matches.
- `mitigation_kinds_present` — at least one active mitigation is of one of these kinds (e.g. `["fail_fast"]`).

## 4. Evaluation (deterministic)

`evaluate(analysis, policy, as_of) -> Suggestions`. Inputs are the projected state (session) or the analyze report (one-shot), a validated policy, and an `as_of` date. Same inputs → byte-identical output.

For each failure mode **not excluded**:

1. **Inherent band** — the policy's matrix cell for unmitigated severity × probability on the analysis's strategy. Unscored → no band, reported as `unscored` with a `research` suggestion.
2. **Residual band** — the cell for the best residual over **active** mitigations (abandoned ones ignored), as the kernel computes it.
3. **Confidence** C0–C4 from the evidence on the mitigations that achieve the residual (best item wins):

   | Level | Meaning | Evidence that reaches it |
   |---|---|---|
   | C0 | Declared only | no evidence, or only `note` items |
   | C1 | Analysed | basis `design`; or kind `file` / `url` without a basis |
   | C2 | Inspected | basis `inspection`; or kind `pull_request` / `commit` |
   | C3 | Tested | basis `test`, or kind `test` |
   | C4 | Proven in use | basis `operational_use` or `failure_history` |

   A failure mode with no mitigations is C0 (nothing reduces it).
4. **Effective band** — the residual band, **unless** confidence is below that band's `min_confidence`, in which case the inherent band (MIL-STD-882E Table VI). Output carries `fallback: {from, to, reason}` when this happens.
5. **Disposition**
   - recorded `accepted` → status `accepted`, with `approver`, `at`, and `review_due = as_of − at > band.review_interval` (band = effective band);
   - recorded `open` → a **suggested** disposition from the effective band's `dispositions`, in this order: `research` if the band allows it and the cause is low confidence/unscored; else `mitigate` if allowed; else `watch` if allowed; else the band's first entry;
   - `rationale_needed = band.no_action_needs_rationale && no mitigation && not accepted`.
6. **Actions** — every catalog action whose `applies_when` holds, sorted by `precedence` (eliminate, prevent, detect, contain, procedure) then `id`; each marked `required` if its `required_when` holds, else `suggested`; each with `tags` and a `why` listing the facts that matched (band, level, domain, confidence, single_point…). Actions already satisfied are not dropped but marked `covered_by: [mitigation ids]` when a mitigation of the matching kind/evidence exists (rule: an action whose precedence is `prevent`/`detect`/`contain` is covered by an active mitigation of kind `prevention`/`detection`/`fail_fast` respectively; `eliminate`/`procedure` are never auto-covered).

Excluded failure modes are listed only in `excluded` with their recorded rationale.

**Analysis-level outputs:**
- `rollups`: counts by effective band, by confidence, by disposition status; `required_uncovered` (required actions with no `covered_by`); `accepted_by_role`; `review_overdue`; `fallbacks`.
- `signoff {pass, reasons[]}`: pass iff no effective band ranks above `signoff.max_residual_band` except accepted risks (when `accepted_counts_as_pass`, and not overdue when `accepted_requires_review_current`), and `required_uncovered` is empty. Each reason names the failure mode and the rule. With `include_kernel_gate`, the kernel's readiness **hygiene** blockers (CLARIFY, weak mitigation order, EMPTY) are added as `kernel: <blocker>`; its residual-zone blockers (`RESIDUAL:`) are not, so `max_residual_band` decides which residuals pass (0.2 final review ruling). Shown **beside** the kernel's `readiness.assess` and `verified` gates, never replacing them.
- `groups` when requested: `failure_mode` | `band` | `tag` | `action`.

**Determinism:** no clock in `fmeca-policy`; `as_of` is an input (the server defaults it to the current UTC date and echoes it). Iteration is in failure-mode id order; maps are ordered.

## 5. Surface (additive; the 0.1 Junior contract is unchanged)

**MCP tool `actions.suggest`** — read-only.
Input: `{ session_id?, analysis?, policy?: string, as_of?: "YYYY-MM-DD", bands?: [string], tags?: [string], required_only?: bool, group_by?: "failure_mode"|"band"|"tag"|"action" }`. Exactly one of `session_id` / `analysis` (handler-enforced; flat schema, no top-level `oneOf`). `policy` is a preset name or a file name in `.fmeca/policies/` (no paths, no `..`); default `compat-0.1`.
Output: `{ policy: {name, hash, class, matrix_derived_from}, as_of, failure_modes: [...], excluded: [...], rollups, signoff, groups? }`.

**MCP tool `policy.list`** — `{ presets: [...], project: [...] }`, each `{name, hash, class, description, source}`; invalid project files are listed with their `error` instead of failing the call.

**CLI**
- `fmeca-mcp suggest (<session-id> | --analysis <file.json>) [--policy <name>] [--as-of YYYY-MM-DD] [--format json|markdown] [--dir <state-dir>]` — exit 0 when sign-off passes, 1 when it does not (usable in CI), 2 on usage/policy errors.
- `fmeca-mcp policy validate <file>` and `fmeca-mcp policy list`.

**Errors** (`invalid_params`, stable prefixes): `POLICY_NOT_FOUND`, `INVALID_POLICY`, `POLICY_STRATEGY_MISMATCH` (no matrix for the analysis's strategy), plus the existing session errors. No silent fallback to another policy.

**Crates:** new `crates/fmeca-policy` depending only on `fmeca`, `serde`, `serde_json`, `toml`, `sha2`; no network, no clock. `fmeca` (kernel) gains nothing. `fmeca-mcp` gains the tools and CLI.

## 6. Presets

Class names echo NASA classes and DO-178C/IEC 62304 tiers without claiming compliance. All presets cover both strategies.

| Preset | Bands (low → high) | Min confidence | Acceptance (suggested) | Required-action tailoring | Sign-off | Review |
|---|---|---|---|---|---|---|
| `compat-0.1` (default) | `none` / `mitigate` (3×3 Medium & High; 5×5 per the kernel's zones) | — | any | none | no `mitigate` residual unless accepted — **equals `readiness.assess`** | — |
| `prototype` | `none` / `report` / `remediate` | — | `owner` | none | no `remediate` residual unless accepted | 365d |
| `standard` | `none` / `compensate` / `review` (maintainer's chart 1) | compensate C1, review C2 | compensate `tech_lead`; review `eng_manager` + `tech_lead` | `design-review` on review | max `compensate` | 180d / 90d |
| `business-critical` | as `standard` | compensate C2, review C3 | review `eng_manager` + `tech_lead`, `product_owner` | prevention required before detection on review; single-point in review must be mitigated | max `compensate`; no single-point in `review` | 90d |
| `safety-critical` | `low` / `medium` / `serious` / `high` (MIL-STD-882E RAC layout) | medium C2, serious C3, high C3 | serious `eng_manager` + `product_owner`; high not acceptable (`elevate`) | design order of precedence enforced; test **and** inspection evidence for serious+; procedural-only mitigation flagged | max `medium` | 90d |
| `confidence-view` | `none` / `report` / `remediate` over **effective band × confidence** (maintainer's chart 2) | — | `tech_lead` | none | no `remediate` | 180d |

`confidence-view` is the only preset whose matrix axes are not S×P: it maps (effective band rank under `standard`, confidence) to a band. It is expressed as a `[matrices.confidence]` table with rows = `standard` band rank and columns = C4…C0, and is the reason the evaluator computes `standard` bands internally first. Exact cell layouts for every preset are fixed in the crate and listed in `docs/policies.md`.

**Action catalog (built-in, shared by presets):** ~25 software actions across tags `design`, `review`, `test`, `ops`, `process`, `docs`, `security`, e.g. design review; ADR for an accepted risk; remove the failure path by design; input validation at the boundary; idempotency key/retry with backoff; contract or property test; fault-injection test; load test; code review by a second engineer; static analysis rule; feature flag + staged rollout; canary + automatic rollback; alert on the leading indicator + runbook; SLO and error budget; dependency pinning/update policy; threat model; penetration test; on-call handoff note. Each with `precedence` and `applies_when`; the full list is part of the presets ticket and reviewed there.

## 7. Skills and docs

- New skill **`fmeca-policy`**: choose a preset, write/validate a custom policy in `.fmeca/policies/`, read bands, confidence, fallbacks, dispositions and sign-off.
- `fmeca-signoff`: call `actions.suggest` under the project's policy and show its sign-off and `required_uncovered` beside the kernel gates.
- `fmeca-resolve`: use suggested dispositions and `review_overdue`.
- Level skills: ask for suggestions grouped by `tag` to propose concrete work.
- `docs/policies.md` (new): the model, the confidence ladder, every preset's cells and catalog, with the sources in §2. README/AGENT-INSTALL: one section each; `.fmeca/README.md` mentions `policies/`.

## 8. Testing

- Golden tests per preset over fixed analyses (both strategies): byte-identical JSON.
- One test per rule: each confidence level; fallback on/off at the threshold; review due/not due as `as_of` moves; disposition suggestion order; `covered_by`; precedence ordering; each sign-off reason; excluded handling; unscored.
- **`compat-0.1` parity:** its `signoff.pass` equals `readiness.assess.ready` on every existing kernel and server fixture.
- Validator: one test per rejection rule (missing band, non-monotone matrix, wrong size, bad `derived_from`, unknown key, bad duration/confidence).
- MCP/CLI: `actions.suggest` schema has no top-level `oneOf`; path traversal in `policy` is rejected; CLI exit codes 0/1/2.
- CI keeps kernel-purity (also asserting `fmeca` does not depend on `fmeca-policy`), the Junior-contract check, and adds `cargo tree -p fmeca-policy` purity (no network/clock crates).

## 9. Out of scope for 0.2 (recorded for later)

- Enforcing approvals, writing policies into the log, any action-taking.
- AIAG-VDA S×O×D Action Priority tables (needs a detection axis).
- Event-driven re-evaluation triggers (design change, new failure data, level advance, policy hash change); 0.2 only computes review-interval staleness from `as_of`.
- A stored per-risk `review_by` or watch triggers on the disposition event.
- Shared/remote policy registries.
- The pending 0.1 follow-up on not-found error codes (-32603 → invalid_params).

## 10. Compatibility

- Junior contract: unchanged (two new tools and new CLI commands are additions).
- Analyses from 0.1.0 work unchanged; `compat-0.1` reproduces today's gate.
- The kernel computation, event log and existing tool outputs are untouched.
